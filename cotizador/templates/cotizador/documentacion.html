1Resumen en una frase

El cotizador es una app de Django llamada cotizador que, a partir de una edad + género (o una cédula que autocompleta esos datos), consulta unas tablas de tarifas en la base de datos y muestra tarjetas comparativas con la prima mensual exacta de cada plan médico. El mismo cálculo lo reutilizan el chatbot y (a futuro) WhatsApp.

Idea clave: no hay precios fijos en el código. Todo — rangos de edad, tarifas y coberturas — vive en la base de datos y se administra desde el panel. El código solo consulta y suma.

3Flujo de una cotización

  1. El usuario entra a /cotizador/. La vista cotizador_view renderiza la plantilla y calcula la empresa por defecto (la primera con planes y con un agente IA activo).
  2. El usuario escribe cédula (opcional) o directamente edad + género.
  3. Si usa cédula → el JS llama a /cotizador/api/cliente/<cedula>/ para autocompletar edad y sexo.
  4. El JS llama a /cotizador/api/cotizar/?edad=..&genero=...
  5. La vista api_cotizar recorre todos los planes activos de la empresa y, para cada uno, pide al motor la prima en variante Básico y Plus.
  6. Devuelve un JSON con planes + primas + coberturas. El JS dibuja las tarjetas.
  7. Al pulsar “Elegir este plan”, se abre el chatbot con el contexto de la cotización ya cargado.

4El motor tarifario

Vive en cotizador/motor_tarifario.py. Es compartido por cotizador, chatbot y WhatsApp. La regla de negocio: la prima depende exclusivamente de edad + género + rango etario + plan + variante dental.

Cómo calcula

  • Rango etario: para una edad, busca el tramo (X-Y) que la contiene. El límite superior es exclusivo — la edad 45 cae en (45-50), no en (40-45); solo el último tramo es inclusivo.
  • Tarifa individual: con (plan, vigencia, rango, género, variante_dental) busca una fila en la tabla Tarifa y toma su prima_mensual. Si no existe, lanza TarifaNoEncontrada (la tarjeta muestra “—”).
  • Grupos: para “titular + 1” o “familia”, la prima total es la suma de las primas individuales.
  • Vigencia: siempre usa la VigenciaTarifaria activa de la empresa (versionado de tarifarios).
# Esencia del cálculo (motor_tarifario.py)
def cotizar(plan, integrantes, variante_dental='basico'):
    vigencia = vigencia_activa(plan.empresa)
    total = Decimal('0.00')
    for integrante in integrantes:
        rango  = rango_para_edad(plan.empresa, integrante['edad'])
        tarifa = Tarifa.objects.get(plan, vigencia, rango, genero, variante_dental)
        total += tarifa.prima_mensual        # suma por integrante
    return total
Multi-tenant: cada Plan pertenece a una empresa (PerfilNegocioIA), así el mismo motor sirve a varias aseguradoras.

7Consulta por cédula

api_cliente_cedula consulta dos fuentes externas con respaldo automático:

1) Broktech (preferida)

POST broktech.com.ec/endpoints/vidanueva/cliente-cedula/ con auth básica (credenciales en variables de entorno VIDANUEVA_USER / VIDANUEVA_PASS).

2) Cotimédica (respaldo)

Si Broktech falla o no responde JSON válido, usa fguerrero.mgaseguros.ec/cotimedica-api/ — la misma que usa el chatbot.

La respuesta se normaliza siempre a {ok, fuente, data:{edad, sexo, nombres, …}} sin importar cuál fuente respondió.

8Integración con el chatbot

Al elegir un plan, el JS abre el widget de chat (/chat-widget/embed.js) y le inyecta un prefacio con contexto: perfil del cliente, todos los planes cotizados con sus precios exactos y el plan elegido. Así el asesor IA no vuelve a pedir la cédula y puede comparar planes y responder dudas usando el RAG.

El agente se resuelve en cotizador_view: se prefiere el agente de la empresa que tenga una herramienta cotizar* activa; si no, el primer agente activo. Se puede forzar con ?agente_id= o ?empresa_id= para montar cotizadores por cliente.

10Arquitectura de la plataforma completa

El cotizador es una app dentro de un proyecto Django mucho más grande (fastchatdj): un CRM con chatbot IA, WhatsApp, voz y campañas. Apps principales por tamaño:

AppRol
crm (~23k líneas)Núcleo: agentes IA, API keys, conversaciones, chat de prueba, consumo de tokens, alertas.
whatsapp (~16k)Integración WhatsApp (webhooks, sesiones, envío/recepción, plantillas).
agents_ai (~6k)Cerebro IA: consultor, proveedores LLM, RAG, memoria, resumidor, auditor, humanización.
seguridad / autenticacionPermisos, roles, usuarios.
agenda / meta / vozTurnos, integración Meta, transcripción de audio (Whisper).
cotizador (~1.2k)Este cotizador médico.
cron_jobsTareas programadas (campañas, recordatorios, reconexión de sesiones).
Navegador / WhatsApp→ Nginx→ Daphne (ASGI)→ Django + Channels→ agents_ai (LLM)→ OpenAI / Gemini / Claude / Ollama

La base de datos es PostgreSQL; Redis es el channel layer de WebSockets (chat en vivo).

11Capa de IA — agentes y proveedores

Todo el LLM vive en agents_ai/. Es multi-proveedor: cada agente elige su proveedor y modelo a través de una ApiKeyIA. Los proveedores están en agents_ai/providers/:

CódigoProveedorModelo por defectoSDK

4Anthropic Claude(configurable)langchain-anthropic
5Ollama (local)gpt-oss:20bChatOpenAI apuntando a Ollama

Agentes especializados

  • Consultor (agente_consultor.py): el chatbot principal. Decide si buscar en RAG, arma el prompt con contexto + historial, llama al LLM y puede usar tools (buscar productos, cotizar).
  • Resumidor (agente_resumidor.py): resume la conversación y analiza sentimiento — mantiene la memoria compacta (menos tokens).
  • Auditor (auditor_agente.py): evalúa la calidad de las respuestas del agente.
  • Acciones IA (ai_actions/): generación de plantillas, campañas WhatsApp, pipelines.
El cotizador y el chatbot comparten el mismo motor tarifario: cuando el cliente elige un plan, el JS le pasa al chatbot el contexto con precios exactos, y el consultor usa el RAG solo para las coberturas.

12RAG — dos sistemas complementarios

FAISS (local, en proceso)

En agente_consultor.py. Índice por agente en disco, cargado en RAM con cache por mtime. Recupera k=5 chunks (de fetch_k=20 candidatos) con MMR (diversidad), deduplica y corta el contexto a 4.000 chars. Embeddings del proveedor del agente.

Weaviate (multi-tenant)

En weaviate_rag.py. Una colección Conocimiento con 1 tenant por empresa (aísla el conocimiento de cada cliente). vectorizer=none: los embeddings los genera Gemini (text-embedding-004 / gemini-embedding-001) y se insertan junto al objeto — así Weaviate no consume CPU/RAM vectorizando. Conexión local 127.0.0.1 con API key.

¿De dónde saca el RAG su información? (fuente del conocimiento)

El conocimiento NO está en el código: lo carga cada cliente desde el panel “Mi Entrenamiento” (crm/view_mientrenamiento.py), y de ahí se indexa al RAG del agente. Fuentes posibles:

FuenteCómo entraDónde termina
Documentos subidos (PDF, DOCX, TXT)Acción subir_documento: se extrae el texto y se trocea (load_and_split).Weaviate (tenant del agente) · o FAISS si es muy grande.
Textos / descripciones del panelSe escriben a mano como fuentes del agente (build_from_string).Weaviate + contexto estático.
Datos del negocio (productos, planes, centros)Comandos indexar_conocimiento / indexar_centros.Weaviate (colección Conocimiento).

El pipeline al indexar: texto → troceo en chunks → embeddings (Gemini) → se guardan en Weaviate junto con metadatos content, source (de qué documento salió), tipo y categoria. Cada agente vive en su propio tenant (agente_<id>), así el conocimiento de un cliente nunca se mezcla con otro.

Enrutado inteligente: documentos grandes → FAISS local + contexto estático; fuentes normales → Weaviate multi-tenant. Al elegir el RAG, el consultor recupera solo los chunks relevantes a la pregunta (no todo el documento) — por eso responde coberturas exactas sin inflar el prompt.
En este servidor el agente activo (id 22) usa RAG Weaviate (tenant agente_22) y el LLM se sirve vía Ollama Cloud (ollama.com) con API key y suscripción fija mensual (gemma4:31b, ministral-3:14b). Por eso el costo por token es $0 (incluido en el plan) y la traza valora el consumo con el equivalente en la nube.

Indexación

Comandos de management: indexar_conocimiento (base de conocimiento) e indexar_centros. Tras reindexar se llama invalidate_vectorstore_cache() para forzar recarga del FAISS.

Ahorro de tokens en RAG: el consultor evita el LLM por completo en saludos y confirmaciones (“hola”, “ok”, “gracias”) con regex, y salta la búsqueda vectorial cuando no aporta.

13Memoria de conversación

Implementada en agents_ai/memoria_django.py como DjangoChatMessageHistory (interfaz de LangChain) respaldada por la tabla MessageStore (session_id, role, content).

  • Guarda cada mensaje humano/IA por session_id; cachea la lista en memoria durante el request.
  • El consultor solo inyecta los últimos 5 turnos (10 mensajes), recortando cada mensaje de usuario a 150 chars y cada respuesta IA a 400 chars — memoria suficiente sin inflar el prompt.
  • El Resumidor comprime conversaciones largas en un resumen, para no arrastrar todo el historial.

15Contabilidad de tokens y costo

Cada llamada al LLM registra un ConsumoTokenIA con: tokens de entrada/salida/total, modelo, origen (whatsapp, chat_crm, webservice, resumidor, sentimiento, auditor…), agente, conversación y un preview del prompt (300 chars).

  • Registro: log_consumo() (en ai_actions/base.py) y _registrar_consumo_tokens() (chat CRM) extraen los tokens del usage_metadata del proveedor.
  • Alertas: AlertaConsumoIA define umbrales diario/mensual por API key; al superarlos notifica.
  • Costo en USD (nuevo): crm/costos_ia.py traduce tokens → dinero. Ojo: este servidor usa Ollama Cloud, que NO se cobra por tokens sino con tarifa plana (Free $0 · Pro $20/mes · Max $100/mes) y límites de uso por GPU-time — sesión (reset 5h) y semanal (reset 7 días), no un tope de tokens. Por eso el costo real por token es $0 y se muestra el equivalente en la nube. Para proveedores de pago por token (OpenAI/Gemini/Claude) sí se calcula el costo real.
Panel de traza: abre /cotizador/traza/ para ver, en vivo, cada request: prompt ejecutado, tokens in/out y costo en USD, con totales del día y del mes por modelo y por origen.

B. Palancas para gastar aún menos

  • Elige el modelo correcto por tarea. El costo por millón varía ~40× entre gpt-4o-mini y gpt-4. Usa modelos mini/flash para chat general y reserva los grandes solo para tareas complejas. Ollama = $0 para lo interno.
  • Baja max_tokens de salida donde no se necesiten respuestas largas (la salida suele costar 3-5× la entrada).
  • Reduce el historial (de 5 a 3 turnos) en flujos transaccionales; resume antes si la conversación crece.
  • Sube el umbral de RAG: recupera k=3 en vez de 5 si las respuestas ya son buenas; menos chunks = menos entrada.
  • Prompt del sistema conciso. El prompt_template del agente se envía en cada mensaje: cada palabra fija se paga siempre.
  • Cachea respuestas frecuentes (FAQ, menú, coberturas) para no repreguntar al LLM lo mismo.
  • Usa embeddings pequeños (text-embedding-3-small) para el RAG: 5-6× más baratos que los grandes.
  • Vigila la traza y las alertas: configura AlertaConsumoIA (umbral diario/mensual) y revisa /cotizador/traza/ para detectar orígenes o agentes que disparan el gasto.
Regla práctica: el costo ≈ (tokens_entrada × precio_in + tokens_salida × precio_out). Los tres factores que más mueven la aguja: modelo, tamaño del prompt fijo y longitud de la respuesta.

C. Optimización aplicada — resultados reales (ago 2026)

Diagnóstico sobre 200 requests: 89% de los tokens eran de ENTRADA (ratio 8×), media 5.255 tok/request, con un runaway de salida de 33.343 tokens. Se aplicó:

CambioDóndeEfecto

Historial 5→3 turnos, salida 3500/3000→2000Config + constantesBaja los casos pesados

22 · Vida BuenaOllama (plan fijo)~2.590 → 2.186

Resultado: desaparecieron los picos de 33k tokens y el consumo por mensaje bajó 15–45% según el agente. En los agentes Gemini eso es ahorro de dinero directo (~−45% en el agente 23). Hallazgo: para agentes con RAG Weaviate el contexto_estatico no se envía (es fallback); el peso real es el prompt de instrucciones + el contexto RAG.
